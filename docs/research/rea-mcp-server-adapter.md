## Summary

- One entry script (`scripts/rea.mjs`) dispatches four modes: `rea mcp` (stdio MCP), `rea mcp --http ...` (streamable HTTP MCP), `rea mcp doctor`, and everything else to the Incur-based CLI. MCP runtime lives in `dist/mcp/main.js` (compiled from `src/main.ts`); CLI lives in `dist/cli-runtime/*`.
- MCP SDK pinned at `@modelcontextprotocol/server` 2.3.1 and `@modelcontextprotocol/client` 2.3.1 (`package.json:358-359`). REA uses the new 2.x API surface: `McpServerFactory`, `serveStdio`, `WebStandardStreamableHTTPServerTransport`, `McpRequestContext` with `era`, `ServerContext.mcpReq.{signal,_meta,notify,envelope}`, Standard Schema (`~standard`) inputs, `maxToolInputElements`, `STDIO_DEFAULT_MAX_BUFFER_SIZE`, `specTypeSchemas`.
- Two runtimes behind one `run()` (`src/main.ts:89-121`): **deferred** (default stdio, no initial target, full output profile, no family scope) boots from a build-recorded, SHA-256-verified catalog JSON and materializes the real server lazily on first tool/prompt/completion call; **eager** (HTTP, `HOPPER_TARGET_PATH`, scoped families, compact output schema, or embedders) composes everything up front.
- Tools are declared once as `ToolContract` objects (name, title, description, kind, Zod input/output schema, effects, derived annotations, `returnsTargetContent`, examples) and registered via `server.registerTool(contract.name, toolRegistrationOptions(contract), handler(contract))`; `createServer.ts` registers ~170 tools grouped under 18 tool-family ids via `registerToolFamilies`.
- Every tool result goes through one `ToolResultDelivery` policy: success = `content:[text JSON]` + `structuredContent` (the Evidence record, including `evidence_id`) + optional `_meta.provenance.untrusted_content`; error = text only, `isError:true`, structured error carrier stripped at the transport; both measured against a byte budget derived from the stdio buffer and replaced by a typed `resource_constraint` error with an `evidence_reference` continuation when they do not fit.
- The server subclass chain is `McpServer` -> `RequestTrackingMcpServer` (tracks in-flight calls for HTTP drain) -> `EvidenceMcpServerCore` (wraps the SDK transport with `ErrorEvidenceTransport` to rewrite SDK errors, compact schemas, retain oversized errors as Evidence, and manage cancellation bookkeeping) -> `EvidenceMcpServer` / `DeferredEvidenceMcpServer`.
- Schema advertisement is tunable per host: `REA_MCP_INPUT_SCHEMA_PROFILE` (compact default, 13 KiB/schema budget; full), `REA_MCP_OUTPUT_SCHEMA_PROFILE` (full default; compact 4 KiB; off), `REA_MCP_TOOL_FAMILIES` (subset of families; out-of-scope tools stay registered but `disable()`d), `REA_MCP_MAX_INPUT_ELEMENTS` (default 1024), `REA_MCP_MAX_RESPONSE_BYTES`. Canonical Zod validation is always enforced server-side regardless of what is advertised.
- Progress: `mcpProgressReporter` adapts `_meta.progressToken` to `notifications/progress`, using an emitted-sequence counter as `progress` (strictly increasing, no `total`), rate limited to 100 ms. Cancellation: `mcpReq.signal` is threaded into every provider call; `notifications/cancelled` is intercepted at the transport so bookkeeping and session admission are released even when the SDK suppresses the reply.
- Identity/discovery: `tools/list` is the canonical catalog and never emits `list_changed` for availability transitions; the `binary_session` tool returns `server_identity` (package, server, SDK versions, negotiated protocol, client, catalog digests, alignment vs caller expectations) plus `tool_availability` groups and `client_features` (elicitation/roots/sampling) read from the request envelope or initialize handshake.
- Transports: stdio is default and the only one registrations/registry describe; HTTP (`/mcp`, loopback by default, one session at a time, newest `initialize` replaces the session, 10 s drain, 8 concurrent dispatches, Host/Origin allowlist, no TLS/auth) is opt-in and also reused by REA's "agent environment" servers (`src/server/environment/serveEnvironment.ts:480`).

## Design choices that make it extensible

- Contract-first tools: `ToolContract` is the single source for name, schemas, effects, annotations, provenance flag, examples; registration (`toolRegistrationOptions`), catalog generation (`scripts/generate-mcp-tool-catalog.mjs`), identity digests (`catalogIdentity.ts`), docs and CLI all derive from it.
- Family registrars with a compile-time-complete map (`registerToolFamilies`) so adding a family forces every call site to handle it, and scoping (`REA_MCP_TOOL_FAMILIES`) is a filter on the same map.
- Injected `RuntimeDependencies` (`serve`, `createServer`, `loadOptionalProviders`, `registerShutdown`, `stdin`) decouples transports and tests from composition; the HTTP path simply swaps `serve`.
- `McpServerFactory` honoured literally: every server instance the SDK creates is owned (`OwnedMcpServers`) and shares one process-owned `BinarySession` and provider set.
- Transport decorator (`ErrorEvidenceTransport`) as the single choke point for wire-level policy: schema presentation, SDK error normalization, budget enforcement, provenance marking, cancellation bookkeeping.
- Delivery policy object (`ToolResultDelivery`) immutable and swappable per server (`withNoTargetRecovery`), with a pluggable `nativeContinuation` strategy for paging.
- Deferred server built from a recorded catalog with Standard Schema shims that lazily resolve to canonical validators, so discovery and execution can have different startup costs without diverging.
- `AsyncLocalStorage` request context (`McpToolRequest`, `AnalysisSettings.run`) lets deep code find the current request's cancellation, validation issues, and settings without threading parameters.
- Optional observation providers loaded independently; load failures are surfaced per-tool as `optionalProviderUnavailable` rather than failing startup.
- Plain HTTP `routes[]` beside `/mcp` reused by agent-environment servers (`serveEnvironment.ts:480-488`).

## What to distill for an observe+drive control plane

- Borrow the contract object: name, Zod in/out schema, explicit effects (`mutatesTarget`, `changesUiState`, `launchesProcess`, `executesForeignCode`, `mayDiscardData`, `idempotent`), derived MCP annotations, `returnsTargetContent`, examples. For a desktop-driving tool, effects like `changesUiState`/`executesForeignCode` map directly onto click/type/launch actions and give hosts a stable basis for approval policies.
- Borrow the result envelope: `structuredContent` = full canonical observation record with content-hash id; text copy of the same JSON; `_meta.provenance.untrusted_content` on anything that echoes screen text, OCR, window titles, clipboard, logs. Pair with server `instructions` that tell the agent to treat that content as data.
- Borrow byte-budgeted delivery with typed overflow errors and a `continuation` (a named follow-up call with arguments) rather than truncation. Screenshots/accessibility trees will overflow stdio frames; retained-evidence references plus a paging/view tool is the right pattern.
- Borrow the cancellation plumbing: one `AbortSignal` from `mcpReq.signal` threaded into every driver call; intercept `notifications/cancelled` at the transport; `cleanup_incomplete` errors listing owned resources; never kill processes you cannot prove you own.
- Borrow progress-as-sequence (no fabricated percentages, `message` carries phase) for long UI automations.
- Borrow `binary_session`-style identity/availability tool: server identity, catalog digest, negotiated protocol, client capabilities, per-tool availability with reasons/remediation, and caller-supplied expectations for alignment checks. Keep `tools/list` stable; report availability out-of-band.
- Borrow schema-advertisement profiles (compact/full input; full/compact/off output; family scoping) if the catalog grows: REA's measured host limits (Moonshot 13 KB/schema, Gemini keyword rejections, Claude Code tool-search-off payload sizes, pi-codemode 16k chars, 1 MiB frames) will apply equally.
- Borrow the HTTP posture: loopback by default, bound-address-class classification, Host/Origin allowlist, explicit opt-in for non-loopback with declared hostnames, one-session-at-a-time with newest-client-wins and bounded drain. Also note what REA explicitly does not do: no TLS, no auth, no multi-user isolation; a control plane that drives a user's desktop over HTTP must add auth or stay stdio-only.
- Borrow the deferred-catalog idea if startup latency matters: record `tools/list` at build, digest it, serve discovery instantly, materialize drivers on first call.
- Avoid/adapt: REA's deep Evidence/session machinery (`withAdmittedAnalysis`, `McpToolRequest.admit`) is tied to its reverse-engineering session model; take the shape (admission scope held through publication) not the implementation. The ~170-tool catalog and six profiles are a real context-cost burden; a control plane should start with few, composable tools.
- Boundary flag: REA's tools are analysis-oriented (static/dynamic RE, decompilers, Frida, debuggers). Nothing in the adapter layer itself defeats DRM or evades controls, but the adapter carries effect flags (`executesForeignCode`, `mutatesDevice`, `mutatesTarget`) precisely so hosts can gate such actions; a control plane should keep and extend that vocabulary and keep the untrusted-content marker so target-derived text cannot steer tool use.

## Constraints & risks

- Only stdio is described by registrations and the MCP registry; HTTP is opt-in, unauthenticated, plain HTTP, single client (`mcp-contracts.md:1070-1086`).
- Deferred runtime depends on a post-compilation digest constant; source runs (undefined digest) always take the eager path (`recordedMcpCatalog.ts:24-27`, `main.ts:107`).
- Startup failures are deliberately redacted to a fixed message; diagnosis requires logs or `rea doctor` (`main.ts:133-138`).
- Several behaviours are workarounds pinned to SDK 2.3.1 quirks (see SDK notes); upgrading the SDK may invalidate them.
- Input admission is a global element count (default 1024) counted by the SDK before validation; large inline payloads must use retained references instead (`mcp-contracts.md:436-466`).
- Compact/relaxed advertised schemas can accept inputs the canonical validator rejects; clients must not rely on advertised schemas for validation (`mcp-contracts.md:1589-1653`).
- `tools/list` does not emit `list_changed` on availability changes; agents must call `binary_session` to learn what is callable now.
- Response budget floor is derived from the stdio buffer even on HTTP (`mcp-contracts.md:1157-1158`).
- Progress notifications are fire-and-forget and only sent if the client supplied a progress token.
- Catalog size: ~170 tools, ~496 KB per request with full schemas on hosts that do not defer tool loading (`client-configuration.md:206-209`).
